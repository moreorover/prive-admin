# Final review fix wave, 23 November 2026

Reviewed the approved personnel and appointment finance design and implementation plan, the whole-branch review package through `5518d92`, and the live appointment creation, assignment, transaction and reporting paths. Implementation commit `f324711` addresses all seven Important findings and the currency-display Minor. The work and verification ran in the original worktree.

## Findings and regression evidence

1. **First master after migration.** An administrator can open a reviewed customer and choose **Register as master** or **Register as assistant**. The customer page displays the existing profile's type and active status. Its route action invokes the owner-only `personnel.create` procedure, which delegates to the existing application service and refreshes the customer detail and personnel list caches. The backfill instructions identify this step for reviewed candidates. Tests cover the administrator, unauthenticated and ordinary-session cases. An integration test starts with zero profiles, provisions existing customer IDs, and verifies the users and accounts tables still contain zero rows.
2. **Master consistency.** The customer appointment route uses the same active-master personnel query builder as the calendar and appointment detail. Search results carry customer IDs. Appointment creation and an explicit master change both require an active profile with type `master`. Title and start-time edits can still be made on historical appointments. The new tests reproduced the unrestricted customer key and both service calls accepting an assistant before the fix.
3. **D1 query limits.** Supporting assignments bind one JSON array. SQLite expands it with `json_each`, deduplicates it, and admits the entire set only when every requested profile is active and every assignment is new. Personnel search uses literal substring matching on lowercased names and phone numbers for both page and count. A six-person insert and a 49-character search containing wildcard characters failed on the original SQL with SQLite's compound-select limit set to five and LIKE pattern limit set to 50. Both pass with the limits enabled and also ran successfully on a disposable workerd D1 binding.
4. **Picker lifecycle.** Confirmation starts the mutation. The route's success handler clears search and closes the picker, unmounting the selection state. A pending request keeps the choices visible. The mounted route test selected Alice and held the mutation response pending, then completed it and reopened the picker. It verified that Alice was excluded and Confirm was disabled. The original implementation lost the visible selection before the response arrived.
5. **Legacy currency.** Appointment rows retain the stored currency. Page totals group by that exact string. An unsupported code is displayed alongside its raw minor units. Ordinary editing and classification are blocked in the UI, service and final update statement. An administrator who has verified the original currency can explicitly confirm a label correction in the dialog. The separate `transactions.resolveCurrency` write compares the transaction ID and previous unsupported currency and updates only the currency column. A stale or repeated correction fails. The amount, counterparty, timestamps, links and classification survive the correction. Regression tests cover the editor, mixed page totals, authorization, compare-and-update behavior and an intervening change to an unsupported currency.
6. **Destination counterparty rules.** Creation and update share the application validator. Received money, refunds and adjustments require the appointment client or linked supporting personnel. An allocation requires an active assigned recipient. A recipient eligible solely through the lead role must still be a master. Update uses the row's stored appointment and counterparty. Both the service and tRPC caller tests reject a received movement for a master outside the allowed recipient set and for an unrelated person.
7. **Eligibility at persistence.** Appointment insert and master change condition the write on the current master profile. The assignment guard rejects a complete mixed batch when any member becomes ineligible or is assigned concurrently. Transaction inserts and updates check the actual appointment, assignment and applicable personnel eligibility in the writing statement. Repository tests intervene immediately before SQL execution to deactivate people, change a profile type, change the lead master, or remove a supporting link. Failed writes preserve the original appointment or transaction and leave no partial assignments. Historical detail and list reads remain available after deactivation.
8. **Exact display and editing.** Finance amounts now format integer minor units without floating-point division. Page totals accumulate with BigInt. The transaction form converts decimal text directly to signed cents and enforces the existing safe-integer write range. Tests cover displaying and editing 9,007,199,254,740,990 minor units, rendered as `€90071992547409.90`, and an exact page sum beyond the JavaScript safe-integer range.

## Delivery notes

The transaction table remains the financial source of truth. The fix wave adds no migration, login creation, compensation calculation, payroll model or ledger. Provisioning and currency correction both require explicit owner action. Currency correction preserves minor units and is appropriate when evidence supports correcting the label.

Verification used disposable local data. The web build retained the existing large-chunk and Mantine Schedule/rrule import warnings. The configured 1Password signing agent failed after the commit checks passed. The fix wave uses a per-commit unsigned fallback. The pre-existing untracked approved spec and plan were read in place.
